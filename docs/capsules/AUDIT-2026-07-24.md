# Capsule Architecture Audit

Date: 2026-07-24  
Scope: `docs/capsules/`, `skills/capsule.md`, the repository's preceding module-architecture rules, adjacent research, and production architecture precedents.

## Executive verdict

**Reshape and test it. Do not ship the current design as a universal architecture.**

The proposal contains a valuable product thesis:

> Give an agent the smallest useful module context, derive the module's actual surface and dependency graph, enforce the allowed boundary, and make the smallest affected verification loop mechanically discoverable.

That thesis is credible and worth a pilot. The present design, however, combines four different boundaries into one directory:

1. code dependency and change impact;
2. agent ownership and work allocation;
3. side-effect authority and security risk;
4. runtime failure and deployment isolation.

Those boundaries sometimes align, but battle-tested systems treat them separately because they have different enforcement mechanisms. Static imports can support the first. They cannot prove the other three.

The design is **not a novel module architecture**. Provided/required interfaces, generated API reports, default-deny visibility, module-local tests, affected graphs, consumer contracts, capability manifests, computed API compatibility, and attestations all have substantial prior art. The potentially novel contribution is the synthesis:

- a generated, position-loaded module brief optimized for coding agents;
- a task-specific work graph derived from verified module facts;
- an explicit promotion path from ordinary folder to enforced module;
- regeneration drills evaluated against an independent, held-out oracle.

That is better described as an **agent-oriented modularity profile and workflow** than a new software architecture.

If “novel” means patent novelty or freedom to operate, this audit is not a legal opinion and the answer should be assumed to be **no until a professional prior-art search says otherwise**.

## 1. What the proposal gets right

Several instincts in the draft are unusually good.

### Generated facts should beat maintained claims

Deriving exports, imports, consumers, and change impact from code is sound. [Spring Modulith](https://docs.spring.io/spring-modulith/reference/fundamentals.html) derives an application-module model with provided and required interfaces. [API Extractor](https://api-extractor.com/pages/overview/demo_api_report/) generates a committed public-API report and makes API review a normal source-control diff. [Buck2](https://buck2.build/docs/concepts/visibility/) has both incoming visibility and outgoing `within_view` constraints. The capsule proposal correctly pulls these mechanisms toward one agent-readable view.

### Position-loaded context is a practical agent affordance

The proposal's small `AGENTS.md` loader and local contract view address a real problem: making the relevant context automatic instead of requiring an agent to decide that it should fetch it. Vercel's focused Next.js evaluation found a large difference between a compact always-loaded documentation index and a skill the agent had to invoke; the result is narrow, but directionally useful ([Vercel evaluation](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)).

### Local verification is more meaningful than green tests in a global environment

A module test that accidentally reaches the whole application does not establish a boundary. [Spring Modulith's module tests](https://docs.spring.io/spring-modulith/reference/testing.html) and [Bazel's hermeticity model](https://bazel.build/basics/hermeticity) show the right direction: declared inputs, controlled environment, and a reproducible target. The capsule draft is right to demand more than a test-name convention.

### Brownfield ratchets are more credible than flag days

The shrink-only idea is supported by experience, but the caveat in the draft is crucial. Shopify's [Packwerk retrospective](https://shopify.engineering/a-packwerk-retrospective) reports static-analysis blind spots, packages that still crashed despite clean static boundaries, long migration periods, and violation lists that became graveyards. A ratchet is useful only when it has owners, expiry, and a measured drain rate.

### The draft admits the behavioral gap

The proposal does not pretend that type signatures describe behavior. That honesty is important. Differential tests, properties, mutation analysis, and characterization corpora can all add evidence. They do not turn a mutable test suite into a complete specification.

## 2. The previous module architecture is the necessary foundation

The capsule proposal did not emerge in a vacuum. This repository already has a coherent module thesis in `skills/architecture-review.md`, `skills/code-standards.md`, and `WORKFLOW_IMPROVEMENT_PLAN.md`.

The available path history first introduces the full capsule dossier in commit `268a053` on 2026-07-24. There are no earlier incremental capsule revisions in Git to evaluate; the research, design, skill, and pilot landed as one conceptual batch. The meaningful predecessor is therefore the repository's July module/workflow policy, not an older capsule implementation.

Its most important rules are:

- create an architecture seam only in response to observed change fan-out, bug clusters, navigation cost, duplicated orchestration, or a missing behavioral test seam;
- use the deletion test: removing a good module removes complexity instead of spreading it into callers;
- prefer deep modules: substantial behavior behind a small interface;
- optimize change locality and caller knowledge;
- classify dependencies before choosing direct calls, substitutes, or adapters;
- keep a feature locally contained and do not reach into another feature's internals;
- avoid barrels that load unrelated modules;
- keep tests at the highest stable public seam, but let tests change when requirements change;
- migrate with expand → consumer-by-consumer movement → contract;
- accept “keep the current shape” as a valid architecture conclusion.

Those rules descend from the durable module tradition: Parnas's information hiding, deep-module thinking, ports at true external boundaries, and modular-monolith practice. Most importantly, they treat a boundary as an **economic hypothesis** that must earn its interface cost.

The capsule draft improves enforcement, but weakens that qualification logic in five places:

1. It starts from a prescribed directory anatomy instead of observed reasons for a boundary.
2. Its mandatory `public.<ext>` barrel conflicts with the repository rule against barrels that force unrelated loading.
3. “One agent per capsule” rewards small ownership units even when they would become shallow modules.
4. A calendar `review-by` trigger conflicts with the earlier evidence-triggered architecture policy.
5. “Removing or relaxing a contract test is major” conflicts with the earlier, sounder rule that tests are deletable when requirements change. The real requirement is an explicit intent change and impact review, not permanent accumulation.

The earlier architecture should therefore be the qualification gate for the new machinery:

> A module earns capsule-like enforcement only after it demonstrates depth, locality, a stable public seam, and enough repeated coordination cost to pay for the contract.

### The lineage and where the capsule thesis changes it

| Architecture thesis | Durable idea | Relationship to the capsule draft |
|---|---|---|
| [Parnas-style information hiding](https://dl.acm.org/doi/10.1145/361598.361623) | Decompose around decisions likely to change, not execution steps | Supports capsules only when the directory hides a real volatile decision |
| Deep modules | Interface complexity must be much smaller than the behavior hidden | Warns against one-agent-per-folder nanocapsules |
| Vertical slices | Keep a user-facing capability and its data/UI/tests locally changeable | The best default for Level 0; often already supplies the desired agent locality |
| DDD bounded contexts | A model and language boundary may justify translation and explicit relationships | Useful for large domain cuts; context-map labels alone do not enforce anything |
| Ports and adapters | Put seams at true external or independently varying dependencies | Argues against fakes/adapters on every in-process capsule edge |
| Modular monolith | Strong logical modules without distributed-system cost | The closest default architecture; capsules should be an overlay on it |
| Build-system target graph | Declared inputs/outputs enable affected tests, caching, and parallel execution | Supplies much of the proposed orchestration and isolation mechanism already |
| Microservices / self-contained systems | Independent deployment and data ownership can justify operational separation | Too expensive if adopted only to make coding agents parallel |
| Runtime cells / actors | Processes, replicas, routing, and supervision contain failures | Orthogonal to source modules and absent from the current proposal |

This matters because “replaceable” has several meanings. A module can be source-replaceable while sharing a process and database. A service can be independently deployable while remaining behaviorally coupled. A runtime cell can contain failure while containing many code modules. The capsule proposal should name which replacement property it establishes at each level instead of treating replaceability as binary.

### Previous rule versus capsule delta

| Previous repository rule | Capsule delta | Audit judgment |
|---|---|---|
| Architecture follows concrete evidence | Capsule anatomy is prescribed up front | Keep evidence as the admission gate |
| Deletion, depth, locality, and test seam qualify a module | Stable boundary and ownership are drafted but unvalidated | Use the full earlier qualification |
| No barrel that forces unrelated loading | Mandatory `public.<ext>` barrel | Require a canonical public path, not a loading strategy |
| Tests are behavioral evidence and may change with requirements | Relaxing a contract test mechanically escalates compatibility | Require intent/evidence review; do not infer semantics |
| Dependency strategy follows in-process/local/remote/external classification | Every consumer tends toward a provider fake | Keep selective dependency-specific strategies |
| Expand → migrate consumers → contract | Freeze all contracts before fleet fan-out | Freeze only changed cut edges |
| Architecture review is evidence-triggered | Review date or churn trigger | Keep churn/escape signals; remove calendar ceremony |
| A valid review may retain the current shape | Capsule creation is positioned as the target state | Make observed/enforced levels optional and reversible |

## 3. Critical design contradictions

### Blocker A — “contracts first” conflicts with generated `provides`

The contract says `provides` is generated from `public.<ext>`, while the fleet workflow says contract diffs land before implementation. There is nothing to generate before the exported code exists.

Pick one:

- make a typed interface or IDL the authored source of truth, then generate provider and consumer bindings; or
- let code remain the source of truth, generate its API report after implementation, and freeze only changed cross-module edges before parallel work.

[WebAssembly Interface Types](https://github.com/WebAssembly/component-model/blob/main/design/mvp/WIT.md) demonstrates the first model: a world explicitly describes imports and exports independently of an implementation. API Extractor demonstrates the second. The current draft claims both.

### Blocker B — the in-file commit signature is self-referential

`CONTRACT.md` proposes writing `signed.at: <commit>` into a file contained by that commit. Git's commit identifier depends on the tree, and the tree depends on that field. Updating the field changes the commit.

Attest the resulting artifact externally instead:

- sign a tree or artifact digest;
- emit a CI attestation attached to the commit, build, or release;
- store it in an attestation service, transparency log, CI artifact, or dedicated ref.

[SLSA provenance](https://slsa.dev/spec/v0.2/provenance) and [Sigstore](https://docs.sigstore.dev/) are better precedents than a mutable `signed:` block.

### Blocker C — imports are dependencies, not capabilities

In a normal Node, Python, Java, or browser process, a module can reach ambient environment variables, filesystem, network, clocks, globals, reflection, dynamic loading, and shared database state without a statically declared import that represents the authority.

Consequences:

- `channels` cannot be reliably derived from imports alone;
- “risk is derived” is only as complete as the observation mechanism;
- a declared low-risk module can invoke a platform helper whose transitive behavior moves money or reads PII;
- a `verify` command does not prove that only declared dependencies were present.

Use security language only when authority is actually constrained through injected handles, OS/container isolation, a component runtime, or an equivalent sandbox. [Fuchsia component manifests](https://fuchsia.dev/reference/cml) and the [WebAssembly Component Model](https://component-model.bytecodealliance.org/design/worlds.html) are examples of declared capabilities with runtime meaning. Without that level, call `channels` an **observed side-effect inventory**, not a capability boundary.

### Blocker D — semantic test relaxation is not mechanically classifiable

The draft says relaxing a contract test mechanically causes a major version. A tool can detect deletion or textual/AST change. It generally cannot tell whether a refactor preserves the assertion, a generator narrowed its domain, an oracle weakened, or two tests were consolidated without behavioral loss.

This is an active limitation of semantic-versioning research: syntactic API changes are far easier to classify than behavioral changes ([2026 systematic review](https://arxiv.org/abs/2605.24397)). Test-aware semantic-versioning ideas exist, including [SEMV](https://semv.readthedocs.io/en/latest/checks/) and Tested Semantic Versioning proposals, so the concept is also not wholly novel. What remains unsolved is dependable semantic interpretation.

Replace “mechanically major” with:

- stable invariant IDs owned by intent;
- a diff that identifies removed or changed evidence;
- a compatibility verdict and affected-consumer query;
- explicit authorization for weakening medium/high-risk intent.

### Blocker E — one capsule cannot automatically be four grains

The best code-dependency boundary may be a large domain. The best work allocation for a task may split that domain or combine it with a consumer. Side-effect authority often cuts across domains. Runtime isolation usually follows processes, tenants, or deployment cells.

Treat these as separate graphs:

1. **code graph** — imports, exports, build/test impact;
2. **authority graph** — network, data, secrets, money, identity, write capabilities;
3. **change-affinity graph** — co-change, runtime calls, ownership, and observed boundary escapes;
4. **mission graph** — the task-specific induced subgraph assigned to agents.

The mission graph can use a module as one work unit when that is efficient; it must not be forced to.

### Blocker F — the pilot cannot prove its claim as designed

The pilot currently builds capsule tooling and the pilot application together, then compares the result to a vaguely defined conventional layout. It has:

- no fixed baseline;
- no matched tasks;
- no randomization or order control;
- no independent acceptance oracle;
- no instrumented foreign-read or undeclared-access measurement;
- no way to separate architecture value from extra tooling effort or task familiarity.

The proposed pilot can demonstrate that a project was built. It cannot attribute the result to capsules.

## 4. Major risks and corrections

### A public entry point is useful; a mandatory barrel is not

A canonical import path is enough. Depending on the language it may be a package export map, package root, facade type, generated binding, named interface, or IDL. A single barrel can increase load coupling, create cycles, and make shallow modules look coherent.

### `verify` needs an isolation implementation

“Run this command in isolation” is not an enforcement mechanism. Use an existing build target or sandbox that declares inputs, tools, environment, and network policy. Bazel, Buck2, containers, or language-specific isolated test fixtures can supply different strengths of proof. The generated report should state the achieved isolation level.

### Static consumer graphs have blind spots

Dynamic imports, events, configuration, reflection, shared storage, database schemas, runtime plugin discovery, and external consumers may not appear in a source import graph. The graph should publish its blind spots and combine:

- static references;
- declared event/schema relationships;
- build metadata;
- observed runtime edges where justified;
- deployment or package-registry consumer data for external interfaces.

“Every consumer” is too strong unless the system controls every possible consumer.

### The platform/kernel will become a coupling sink unless budgeted

“Platform has zero capsule dependencies” prevents cycles but not a god kernel. Track:

- platform API and change rate;
- transitive authority and risk;
- fan-out and affected closure;
- domain-specific concepts leaking into platform;
- percentage of work that requires platform edits.

High fan-in is not inherently bad—a stable clock, logger, or type can appropriately have high fan-in. High fan-in plus churn is the warning.

### Graph depth is a signal, not automatically a performance bug

Dependency depth affects build scheduling and cross-module coordination when work traverses the chain. It is not the same as application latency or agent wall-clock for every task. Hard-capping depth tends to push coupling into shared kernels, event buses, or databases. Measure task critical paths; do not optimize an abstract graph number.

### Fakes should be selective

A provider-verified fake is valuable when the dependency has stable, locally reproducible semantics. It is expensive or misleading for remote services, queues, time, concurrency, large data stores, and failure modes. Use the dependency classification from the earlier architecture:

- direct in-process dependency → call it directly in a module test;
- deterministic local substitute → owner-verified fake;
- remote-owned API → provider contract, recorder/simulator, or sandbox;
- true external system → port plus targeted integration evidence.

### “Pending expectations without the broker” omits the hard part

Pact's pending behavior depends on version, branch, deployment, and verification relationships in the [Pact Broker matrix](https://docs.pact.io/pact_broker/advanced_topics/pending_pacts). An in-repo file can represent a pending source change, but not automatically “what is safe to deploy where.” Use the lighter model only for a single-version monorepo and say so.

### Internal semantic versions may be ceremony

If every module is built, tested, and released together, there is no independent resolver choosing compatible module versions. In that case a compatibility verdict plus affected-consumer closure is more useful than `1.2.0`. The [bnd baselining guidance](https://bnd.bndtools.org/chapters/180-baselining.html) explicitly notes that baselining can be overkill when a project is always compiled with its dependencies and has no external consumers.

Version modules only when they have independently released consumers, cache identities, parallel supported versions, or a real compatibility policy.

### Code isolation is not runtime isolation

AWS [cell-based architecture](https://docs.aws.amazon.com/solutions/cell-based-architecture-on-aws/) limits production blast radius with independent replicas and routing. Erlang/OTP applications and supervisors address startup, restart, and failure containment ([OTP applications](https://www.erlang.org/docs/18/design_principles/applications)). A capsule directory supplies neither. Use “change isolation” for the current goal; reserve “fault isolation” for a runtime mechanism.

### Regeneration is vulnerable to spec laundering

The same agent can change code, weaken tests, and produce a green result. Differential testing preserves old bugs as easily as desired behavior. Mutation score measures the chosen mutants and oracle, not product intent; equivalent mutants and operator selection complicate interpretation. Automated program-repair studies report substantial test-suite overfitting, but those benchmark-specific rates do not mean that a capsule has a universal “70% behavioral freedom.”

Regeneration must remain an experiment with a separate intent owner and a held-out oracle. Do not grant zero-review merge authority from the current gate stack.

### One mixed contract file has incompatible lifecycles

Authored intent, generated facts, and CI attestation change for different reasons and have different owners. Mixing them in one tracked frontmatter block creates noisy diffs and signature churn. “No shadow truth” is correct; “only one physical file” is not necessary.

Use:

- one small authored policy;
- a language-native API/IDL as the public source;
- one generated report derived from policy and code;
- one external attestation derived by CI;
- a generated one-page `CONTRACT.md` view for agents.

There is still one source for each fact, without forcing all facts into one lifecycle.

### Evidence quality correction

The capsule dossier sometimes treats 2026 preprints and single-project observations as battle-tested evidence. They are useful hypothesis generators, not production validation.

For example, the Forge work reports fewer navigation steps and more consistent behavior with formal descriptors, but its author also lists an N=1 field setting, a same-session A/B test with no significant effect, and untested multi-agent coordination ([author limitations](https://ruoqijin.com/research/forge)). Its S-expression/YAML result concerns injected structural writer errors; it does not establish that S-expressions improve agent navigation. Schema validation matters more than choosing a fashionable syntax.

The source cited in `research/llm-era.md` for the Vercel skill result is also misattached: [arXiv 2601.11564](https://arxiv.org/abs/2601.11564) studies irrelevant context length, while the 100%/79%/53% and skill-invocation observations come from the separate Vercel evaluation linked earlier.

## 6. Recommended architecture: an earned module-enforcement ladder

Do not force every feature to become a full capsule. Promote a boundary only when its value and required proof justify the cost.

### Level 0 — contained feature

- feature folder owns code and tests;
- no cross-feature internal imports;
- ordinary repository context;
- global test/build tooling.

This remains the default for new or rapidly changing product work.

### Level 1 — observed module

- generated exports, imports, consumers, side-effect observations, and change-affinity report;
- a stable canonical import path;
- a local verification command is discoverable;
- no new enforcement or semantic version.

Purpose: gather evidence in shadow mode without creating contract ceremony.

### Level 2 — enforced module

- explicit allowed dependency policy;
- default-deny private internals;
- build/lint enforcement;
- reproducible local verification target;
- generated affected-consumer closure;
- owner and temporary escape lifecycle.

Purpose: change isolation and reliable task scoping.

### Level 3 — contracted component

- independently authored typed interface or stable public API report;
- explicit intent invariants with IDs;
- compatibility and consumer-impact checks;
- consumer/provider contract workflow where independent evolution warrants it;
- independent release version only if the economics require one.

Purpose: allow provider and consumers to evolve independently.

### Level 4 — sandboxed capsule

- runtime receives only declared capabilities;
- filesystem, environment, network, secrets, and services are actually restricted;
- transitive authority drives risk;
- provenance and policy are externally attested;
- failure/deployment isolation is stated separately and tested where claimed.

Purpose: security or replacement boundaries. This is where the word “capsule” has its strongest technical meaning.

### Promotion test

A module should move up a level only when evidence answers yes to the relevant questions:

1. Does deletion remove a coherent capability instead of scattering its logic?
2. Is the interface deep enough to reduce caller knowledge?
3. Do most changes stay inside the proposed boundary?
4. Is there a stable public behavioral test seam?
5. Has coordination, independent consumption, security, or regeneration created enough recurring cost to pay for the next level?
6. Can the intended enforcement actually be implemented in this language/runtime?

Demotion, merging, and splitting are valid outcomes. A boundary is not a promotion forever.

## 7. Revised artifact model

Example names are placeholders; do not standardize them before the pilot.

### Authored policy

```yaml
schema: module-contract/v1
module: exposure
level: enforced
intent:
  - id: EXP-SORT-001
    statement: Exposure rows are sorted by descending weight.
allowed_dependencies:
  modules: [pricing]
  platform: [api-client, design-tokens]
allowed_authorities:
  - api.reserve.org:read
owner: exposure
exceptions: []
```

This file contains decisions only. Its schema version is distinct from any independently released API version.

### Public source

Use the strongest native representation:

- TypeScript package exports plus API Extractor;
- Java package/named interface;
- Python public package and type stubs;
- OpenAPI/Protobuf for a network boundary;
- WIT for a real component boundary.

Do not invent a lowest-common-denominator function-signature string in YAML.

### Generated module report

Generate:

- actual exports and canonical API digest;
- actual static dependencies and known dynamic blind spots;
- observed side effects and evidence source;
- consumer/affected closure;
- local verification target and achieved isolation level;
- co-change/churn indicators;
- policy violations and expiring exceptions.

Render the compact parts into `CONTRACT.md` for automatic agent loading. Do not edit generated facts by hand.

### External attestation

CI signs the source tree/artifact digest, generated report digest, verifier identity/version, and command result. It does not write its own commit ID back into the commit.

## 8. New workflows enabled by the corrected thesis

### Workflow 1 — Observe → earn → enforce

1. Generate a shadow module graph over the existing feature layout.
2. Record cross-boundary reads, churn, and false affected predictions.
3. Nominate only boundaries with repeated cost.
4. Apply the depth/deletion/locality qualification.
5. Enforce one boundary at a time.
6. Promote, merge, split, or abandon it based on measured effects.

This tests the thesis without front-loading ceremony.

### Workflow 2 — Task-shaped mission graph

1. Map the requested behavior to the code graph.
2. Compute the affected subgraph and its cut edges.
3. Freeze only public edges that the task changes.
4. Assign agents by cohesive work packets, not one agent per permanent module.
5. Give each worker write access to its packet and read-only access to the necessary contract views.
6. Recompute the graph and verify cut edges at convergence.

This preserves parallelism without manufacturing nanomodules.

### Workflow 3 — Contract-first only at changed edges

1. A consumer proposes an intent example or typed API delta.
2. CI compiles or validates both sides against that proposal.
3. The provider accepts, rejects, or counters the edge.
4. Once accepted, provider and consumer implementations proceed in parallel.
5. Unchanged modules do not rewrite or re-approve contracts.

This keeps exploration cheap and coordination explicit where it matters.

### Workflow 4 — Authority-scoped agent execution

1. Start the agent in a worktree or sandbox with a bounded write mount.
2. Make other module internals unavailable or read-only.
3. Expose declared external services through named handles or proxies.
4. Log actual filesystem/network/service access.
5. Compare observed access with policy.
6. Treat undeclared access as either a missing policy decision or a wrong boundary.

This turns “stay in your capsule” from a prompt into evidence.

### Workflow 5 — Intent-preserving contract change

1. Stable invariant IDs tie prose intent to tests/properties.
2. A test deletion or oracle change reports which intent IDs lost evidence.
3. CI computes affected consumers and usage.
4. Low-risk evidence refactors can be acknowledged normally.
5. Intent weakening requires a named decision and stronger authorization by risk.
6. Old evidence is archived in history, not accumulated forever.

This is more honest than pretending semantic relaxation is mechanically known.

### Workflow 6 — Regeneration tournament

1. Keep the old implementation and produce two or more candidates.
2. The implementation agent sees the public intent and training corpus only.
3. A separate evaluator owns held-out examples, metamorphic properties, security cases, and operational constraints.
4. Differential results are classified: required preservation, accepted correction, or unexplained divergence.
5. Candidates run in shadow or canary mode where the system permits it.
6. A human reviews the evidence until a substantial track record justifies narrower automation.

Mutation testing is a diagnostic input, not the merge authority.

### Workflow 7 — Boundary health loop

Track:

- foreign internal reads;
- undeclared dependency and authority attempts;
- internal versus external co-change;
- contract and policy churn;
- platform edits caused by module work;
- affected-set false negatives and false positives;
- fake/simulator drift;
- temporary exception age;
- module test isolation failures.

Use the signals to promote, merge, split, demote, or move a capability. Do not use a calendar review as the primary trigger.

### Workflow 8 — Rebuildability drill

Periodically give a cold agent one stable module, its generated view, the task, and the allowed dependencies. Score navigation, questions, correctness, and boundary escapes. This tests context sufficiency without granting automatic replacement authority.

## 9. Which battle-tested architecture to use when

| Need | Default architecture | Where the capsule profile helps |
|---|---|---|
| Fast-moving product feature | Vertical slice / contained feature | Local agent context and observed graph only |
| Large in-process application | Modular monolith; Spring Modulith-like checks | Generated brief, affected task routing, boundary health |
| External I/O substitution | Ports and adapters / functional core, imperative shell | Authority inventory and stable intent tests |
| Large monorepo build/test scope | Bazel, Buck2, Nx, or equivalent project graph | Agent-readable view and mission-graph orchestration |
| Independently evolving network services | OpenAPI/Protobuf + consumer contracts | Intent IDs and agent work routing |
| Plugin or language-neutral component ABI | WIT/Component Model, OSGi/JPMS where appropriate | Position-loaded context and regeneration drills |
| Strong capability security | Fuchsia-like routing, Wasm sandbox, process/container controls | Risk view and attestations |
| Runtime fault containment | OTP supervision, bulkheads, cells, queues, process isolation | None automatically; keep as a separate graph |
| Tenant/deployment blast radius | Cellular architecture | Capsule terminology should not obscure the operational cell |
| Supply-chain proof | SLSA/in-toto/Sigstore | Attach module report and verification evidence |

The durable recommendation for most repositories is:

> Start with a well-designed modular monolith and an existing build graph. Add the agent-oriented generated view and mission workflow. Escalate to contracts or runtime capsules only for boundaries that demonstrate the need.

## 10. A controlled pilot that can answer “would this work?”

### Hypotheses

H1. A generated local module view reduces foreign-file reads without reducing task correctness.

H2. Enforced allowed-dependency rules catch boundary escapes earlier than normal review and integration tests.

H3. A task-shaped mission graph reduces net wall-clock time for genuinely parallel cross-module changes after contract/setup time is included.

H4. Promotion-level maintenance costs remain below the coordination and defect costs they remove.

H5. A held-out regeneration drill can identify candidate regressions that the visible contract suite misses.

### Experimental shape

1. Choose an existing application with several already-understood domain seams. Greenfield work makes boundary correctness too easy to rationalize after the fact.
2. Run shadow graph generation first; do not enforce or refactor.
3. Select matched task pairs across:
   - local behavior changes;
   - one-provider/one-consumer changes;
   - three-or-more-module features;
   - one dynamic/event/storage interaction;
   - one low-risk regeneration drill.
4. Compare:
   - A: current best-practice vertical slices and ordinary workflow;
   - B: generated module brief only;
   - C: brief plus enforced boundary and mission graph.
5. Randomize condition order or use separate equivalent tasks to limit learning leakage.
6. Keep acceptance tests and some fault cases hidden from implementation agents.
7. Include all setup, contract negotiation, retry, and maintenance time in the result.

### Measures

- accepted task correctness on held-out evidence;
- total human and agent wall-clock;
- model tokens/tool calls;
- foreign internal reads;
- undeclared dependency/authority attempts caught at lint, local verify, integration, review, or production;
- affected-set false negatives and false positives;
- contract/policy maintenance share of task time;
- manual steering and clarification count;
- change fan-out and merge conflicts;
- post-change defects;
- regeneration divergences found by visible versus held-out evidence.

### Pre-register thresholds

The exact numbers should be chosen before running tasks, not after seeing results. A reasonable starting decision policy is:

- no accepted affected-set false negatives for enforced modules in the pilot;
- a material reduction in foreign reads with no correctness loss;
- a meaningful net wall-clock improvement on parallel tasks after coordination cost;
- contract/policy work below a fixed minority of total task effort;
- almost all synthetically seeded structural escapes caught before integration;
- no zero-review regeneration authority until many shadow replacements survive held-out and real-use observation.

If the generated brief helps but enforcement does not pay, keep Level 1 and stop. If enforcement helps but contracts do not, stop at Level 2. A partial result is a successful pilot.

## 11. Claim-by-claim final judgment

| Claim | Judgment |
|---|---|
| A generated local contract view can reduce agent navigation | Plausible and supported enough to test |
| Derived imports/exports can make structural boundaries reliable | Yes, within static-analysis limits |
| A capsule can be locally verified | Yes, if isolation is implemented, not declared |
| Static dependencies can derive security capabilities/risk | No, not in an ambient-authority runtime |
| One boundary should equal ownership, parallelism, regeneration, and verification | No |
| Contracts should precede all implementation | No; only changed public cut edges need freezing |
| Contract tests are part of compatibility evidence | Yes |
| Test relaxation can be mechanically identified as a breaking change | Not generally |
| Per-module semantic versions help a single-version monorepo | Usually not |
| Fakes enable safe parallelism | Sometimes, for carefully chosen dependencies |
| Pending expectations need no broker semantics | Only in a simplified single-repo lifecycle |
| Mutation + differential tests permit zero-review regeneration | Not established |
| Flat graphs maximize fleet throughput | Too absolute |
| The current combination is wholly unoccupied ground | No |
| The agent-context + mission-graph + promotion workflow may be novel | Possibly; validate and describe narrowly |

## Recommendation

Continue the work under a narrower thesis:

> **Verified module workspaces** turn existing, economically justified module boundaries into generated agent context, enforceable change scopes, and task-specific collaboration graphs.

Keep “capsule” for Level 4 or as a project codename until the naming collision is resolved. The space already includes [Capsule Security](https://docs.capsulesecurity.io/guides/architecture-overview), [Agent Capsule Protocol](https://agentcapsuleprotocol.com/), the separate [Agent Capsule](https://www.agentcapsule.app/) checkpoint product, and older container “capsule” designs such as [OpenStack Zun's composition proposal](https://opendev.org/openstack/zun/src/commit/a7edf83c8a93fec9dec5a0cbb64e4d3f07e94661/specs/container-composition.rst). The current “appears unclaimed” statement is not defensible.

The next implementation should build only:

1. a shadow-mode graph/report adapter for one stack;
2. one generated local `CONTRACT.md` view;
3. one existing-tool boundary rule;
4. one reproducible local verification target;
5. an instrumented matched-task pilot.

Defer semantic versions, pending expectations, verified fakes, mutation thresholds, signing, runtime capabilities, and automatic regeneration until the lower levels independently demonstrate value.

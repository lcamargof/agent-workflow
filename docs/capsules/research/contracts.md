# Research: Contract-Verification & Interface-Evolution Systems

Provenance: research-agent sweep, 2026-07-24. Preserved verbatim as evidence base; synthesis lives in `../prior-art.md`.

## 1. Pact / Consumer-Driven Contract Testing

**(a) Mechanism.** Consumer unit tests run against a Pact mock; each interaction (request + expected response with matchers) is recorded into a JSON pact file. Provider verification replays those requests against the real provider and compares responses. **Pact Broker** stores pacts + verification results per app version/branch; the **Pact Matrix** is the grid of (consumer version × provider version × result). **can-i-deploy** queries the Matrix against what's recorded as deployed per environment (`record-deployment`). **Provider states** ("given user 123 exists") map to provider-side data-setup callbacks — the main provider cost. **Pending/WIP pacts**: new consumer expectations are verified but don't fail the provider's build; they only block the consumer's own deploy. (https://docs.pact.io/, https://docs.pact.io/pact_broker/can_i_deploy, https://docs.pact.io/pact_broker/advanced_topics/pending_pacts)

**(b) Mechanical vs social.** Mechanical: replay, Matrix, deploy gating, pending semantics. Social: which interactions get contracts, matcher looseness, provider-state honesty, and — decisively — cross-team buy-in. PactFlow's own post: "The number one reason that Pact implementations fail is a lack of buy in from all the parties." (https://pactflow.io/blog/why-pact-implementations-fail-and-what-you-can-do-to-avoid-it-blog/)

**(c) Breaking vs compatible.** Defined empirically **per consumer**, not by schema rules: a change is breaking iff it fails replay of some consumer's recorded interactions, cross-checked against what's deployed where. You can delete a field no consumer recorded and stay green.

**(d) Failure modes / abandonment — the famous part.**
- PactFlow's five-reasons posts: lack of buy-in, education gap, cost/benefit misalignment (testers pay, devs benefit), partial adoption, leadership skepticism (https://pactflow.io/blog/five-reasons-why-your-contract-testing-initiative-could-fail-and-how-to-avoid-them/).
- Practitioner retrospective (Jan 2026): after 3 months the team stopped trusting Pact as sole defense — happy-path-only contracts, **Broker down twice blocking all deploys** (SPOF), slow hard-to-diagnose failures (https://medium.com/@codexlab/contract-testing-with-pact-looked-good-broke-anyway-3774270bdd15).
- Speakeasy analysis: heavy initial undertaking; "Pact separates the responsibility for the contract from the responsibility of maintaining the service"; N consumers write overlapping tests. Verdict: fits large orgs with many internal services and strong inter-team channels; schema-based approaches for everyone else (https://www.speakeasy.com/blog/pact-vs-openapi/).
- Pact's own FAQ concedes: not for public APIs, not when the other team won't participate — works best when one org/team owns both sides (https://docs.pact.io/faq).
- "Dependency drag": consumer must exist and publish before provider can verify — kills parallel development (https://specmatic.io/updates/pacts-dependency-drag-why-consumer-driven-contracts-dont-support-parallel-development/).
- Spotify's testing-honeycomb post mentions Pact only as a future aspiration, never adopted publicly (https://engineering.atspotify.com/2018/01/testing-of-microservices). No citable "Spotify abandoned Pact" source exists.
- **The strongest signal: PactFlow's pivot.** The post literally titled "Pact is dead, long live Pact" launched **bi-directional contract testing**: provider uploads its OpenAPI spec + evidence its own tests verify it; PactFlow statically checks "consumer contract ⊆ provider contract." No replay, no provider states — the CDC company shipped a schema-based mode because full CDC's coordination cost only pays with universal buy-in (https://pactflow.io/blog/bi-directional-contracts/). Counterweight, also PactFlow (Matt Fellows): "Schemas are not contracts" — schemas are abstract, contracts are concrete examples; schemas allow drift and under-specify (https://pactflow.io/blog/schemas-are-not-contracts/, series: https://pactflow.io/blog/contract-testing-using-json-schemas-and-open-api-part-1/).

**(e) Steal.** can-i-deploy: compatibility as a queryable matrix keyed to *what's actually deployed where*, plus pending/WIP as the best-designed "unmet-expectation lifecycle" — a new expectation can exist, visibly fail, and block only its author. Also: "consumer-needs ⊆ provider-guarantees" as a mechanical compatibility relation that decouples teams.

## 2. OpenAPI/AsyncAPI as Contracts

**Schemathesis.** (a) Derives Hypothesis property-based fuzzers from OpenAPI/GraphQL specs; checks generic properties (no 5xx on schema-valid input, response matches declared schema, invalid input rejected, stateful sequences via links) against the live implementation (https://github.com/schemathesis/schemathesis). ICSE 2022 paper (arXiv 2112.10328): only tool handling >2/3 of 16 real targets; 1.4–4.5× more unique defects than second-best per target (https://arxiv.org/abs/2112.10328). (b) Implementation↔spec conformance is mechanical; spec *quality* is social — a bare `type: string` fuzzes nothing meaningful. (c) Not diff-based; "breaking" = observed divergence at test time. (d) Noise on loose specs; needs runnable service + auth/data; typical first run finds 5–15 issues, i.e. most specs are already wrong (https://qaskills.sh/blog/schemathesis-property-based-api-testing-guide-2026). (e) **The spec is a generator, not just a validator** — thousands of executable checks from zero hand-written cases.

**Dredd.** Replays the spec's documented examples as HTTP requests. **Archived read-only Nov 8, 2024** with 211 open issues (https://github.com/apiaryio/dredd). Lesson: example-replay is the weakest executable-spec form — one hand-typed happy-path case per operation, dies when examples rot; generation strictly dominates it.

**oasdiff / openapi-diff.** (a) Static diff of two OpenAPI docs against a rule catalog: **506 change types — 212 breaking, 30 warnings, 264 informational** (https://github.com/oasdiff/oasdiff, https://www.oasdiff.com/docs/breaking-changes). (c) Direction-sensitive: requests contravariant (adding required param / tightening = breaking), responses covariant (removing/narrowing = breaking; adding optional = fine); endpoint removal breaking unless it went through `deprecated: true` + sunset. (d) Spec↔implementation drift upstream is invisible (that's Schemathesis's job); no usage awareness so it over-reports removals nobody uses (Pact's relativity is the complement). (e) An **enumerated, versioned rulebook of change types generated from the checker itself**, so docs can't drift from enforcement.

**Spec-first vs code-first.** No knockout winner; surveys lean spec-first for design (https://www.readysetcloud.io/blog/allen.helton/seriously-write-your-spec-first/), code-first dominates framework land. Honest resolution: both camps drift (spec-first specs rot; code-first specs faithfully document accidents) — the debate resolved by **enforcement**, not by picking a side: make the spec load-bearing (gateway generated from it: https://zuplo.com/learning-center/openapi-first-api-gateway) or continuously fuzz implementation against spec in CI (https://netapinotes.com/navigating-openapi-typespec-and-api-drift-in-the-post-openapi-era/).

## 3. Protobuf + buf

**(a) Mechanism.** `buf breaking` diffs the current schema against a baseline — git ref (`--against '.git#branch=main'`), BSR module, or image — with effectively zero config (`breaking: use: [FILE]` default) and a fixed enumerable ruleset: same input, same verdict (https://buf.build/docs/breaking/). The **BSR** enforces policy server-side: a breaking push to main goes to a "Pending" state, invisible to consumers, until an owner approves in a review flow (https://buf.build/docs/bsr/checks/breaking/, https://buf.build/blog/review-governance-workflow).

**(c) Breaking = a lattice of named categories tied to a concrete consumer model** (https://buf.build/docs/breaking/rules/), FILE ⊃ PACKAGE ⊃ WIRE_JSON ⊃ WIRE:
- **FILE** (default): per-file generated source doesn't break (C++/Python imports) — `FIELD_NO_DELETE`, `MESSAGE_NO_DELETE`…
- **PACKAGE**: allows moving definitions between files (fine for Go).
- **WIRE_JSON** (recommended minimum): binary and JSON stay decodable — `FIELD_SAME_NAME` (JSON keys), `FIELD_NO_DELETE_UNLESS_NUMBER_RESERVED`.
- **WIRE**: binary only — int32↔int64-class interchange allowed; deleting a `reserved` range is itself breaking (re-opens numbers).

gRPC evolution rules (https://protobuf.dev/best-practices/dos-donts/): **never reuse a tag number**; on deletion `reserve` numbers *and* names; almost never change field type or default ("causes version skew"); unknown-field preservation lets old intermediaries forward new fields (proto3 initially discarded unknowns — real breakage forced reintroduction in v3.5: https://kmcd.dev/posts/protobuf-unknown-fields/). **`required` considered harmful**: removed from proto3 entirely; Buf's "required is forever" post — checked at every hop, so a middleman that never reads the field still drops the message; root cause of early Google outages (https://buf.build/blog/totw-8-never-use-required).

**(b/d).** Mechanical: everything structural + server-side gating. Social: field *semantics* — Google's own guidance is "Never add a required field, instead add `// required` to document the API contract," i.e. the real contract lives in comments. Custom options are out of scope by design; behavioral change behind an unchanged schema is invisible; the `required` saga is the ecosystem's cautionary tale of a mechanically-checkable constraint that was operationally catastrophic.

**(e) Steal.** Buf never asks "is this breaking?" — it asks "breaking *for whom*," as named opt-in rule bundles diffed against a git ref, with "pending until human review" (BSR) as the escape hatch instead of a config knob.

## 4. GraphQL Federation / Apollo Schema Checks

**(a) Mechanism.** `rover subgraph check` in CI runs (1) **composition checks** (does the subgraph still compose into a valid supergraph) and (2) **operation checks** — the differentiator: the diff is validated against **observed client traffic**. Routers report operation metrics to GraphOS; a check replays the last N days of distinct real operations against the new schema and fails only on actual collisions — `FIELD_REMOVED` fires only when "a field used by at least one operation was removed" (https://www.apollographql.com/docs/graphos/platform/schema-management/checks, https://www.apollographql.com/docs/graphos/platform/schema-management/checks/reference). `@deprecated` → watch usage on Insights → remove at zero. **Persisted query safelists** turn the open query surface into a closed enumerable consumer set (https://www.apollographql.com/docs/graphos/routing/security/persisted-queries). OSS alternative: GraphQL Inspector — breaking/dangerous/safe classification, optional `considerUsage` (https://the-guild.dev/graphql/inspector/docs/commands/diff).

**(c) Breaking.** A property of the (change × observed usage) pair, not the change alone. Federation v2 composition rules: shared fields need `@shareable`; output types merge by union, input types/args by **intersection**; the **satisfiability** rule guarantees every field is resolvable via every query path (https://www.apollographql.com/docs/graphos/schema-design/federated-schemas/reference/composition-rules).

**(d) Failure modes.** **Traffic-window blind spots**: default window ~1 week, plan-gated history — monthly jobs, year-end flows, slowly-updating mobile clients are invisible; Apollo's own tuning advice (shrink window, raise min-request threshold) buys speed with more blind spot (https://www.apollographql.com/docs/graphos/platform/schema-management/checks/configure). Unobserved consumers (no metrics reporting) are unprotected; zero-traffic variants degrade to block-everything or check-nothing. Contract variants silently broke until dedicated contract checks were added (https://www.apollographql.com/blog/prevent-breaking-changes-in-downstream-variants-with-contract-checks). Resolver behavior changes behind identical SDL pass everything.

**(e) Steal.** Check changes against a **recorded corpus of real interactions**, make the corpus's coverage window a first-class visible parameter, and use safelisting to convert unknown consumers into an enumerable set — closing the exact blind spot observed-traffic checking leaves.

## 5. Semver Enforcement Tooling

**cargo-semver-checks.** (a) ~100+ lints as Trustfall queries over rustdoc JSON, baseline = what's actually on crates.io (https://github.com/obi1kenobi/cargo-semver-checks). (d) Documented false negatives: type changes in signatures, generics/lifetimes, feature-gated APIs, all behavioral changes; cross-crate re-exports cause ">90% of real-world false positives" (https://rust-lang.github.io/rust-project-goals/2025h1/cargo-semver-checks.html). **The study** (Gruevski): top 1,000 crates, 14,389 releases since 2017 → 3,062 verified violations; **~1 in 31 releases and >1 in 6 crates shipped a semver violation** — a lower bound; verified via generated "witness" programs that compile on old, fail on new (https://predr.ag/blog/semver-violations-are-common-better-tooling-is-the-answer/). On the official Rust roadmap to run inside `cargo publish` by default (https://rust-lang.github.io/rust-project-goals/2024h2/cargo-semver-checks.html). (e) **Witness programs**: every claimed breakage emits an executable counterexample.

**japicmp / Revapi (Java).** (a) Bytecode-level diff (javassist) / richer API-model diff; Maven plugins fail the build when the declared bump is smaller than the diff requires (https://siom79.github.io/japicmp/, https://revapi.org/revapi-site/main/index.html). (c) The important subtlety: every difference is classified against **both binary compatibility (JLS ch. 13** — precompiled callers keep linking) **and source compatibility** (recompilation works) — the sets don't coincide (new overload: binary-OK, source-ambiguous). Revapi supports reviewed "this break is intentional" waivers. (d) Behavioral/reflection-mediated contracts invisible; accuracy gaps documented in the Roseau comparison (https://arxiv.org/pdf/2507.17369). (e) The **two-audience compatibility matrix** + a recorded waiver system.

**api-extractor (TS).** (a) Emits a generated `.api.md` public-surface report **checked into git**; stale report fails CI; every export needs a release tag (`@public`/`@beta`/`@alpha`/`@internal`) (https://api-extractor.com/pages/overview/demo_api_report/). (b) The breaking-change judgment itself is **social by design**: branch policy requires API-steward sign-off on any `.api.md` diff; the tool never computes "this is major." (c) Structural typing makes "breaking" genuinely fuzzy — the community formalization is Semver-for-TypeScript-Types / Ember RFC 730, which had to define breaking per variance position (https://www.semver-ts.org/). (d) No bump enforcement; inference-level breakage escapes the printed report. Complement: **attw** verifies the *published tarball* under every resolution mode (https://github.com/arethetypeswrong/arethetypeswrong.github.io). (e) A generated, diff-minimal contract artifact whose **git diff is the review interface**, with graduated strictness by maturity tag; verify the shipped artifact, not the source tree.

**Elm — the purest example.** (a) The package manager records the full types of everything exposed; `elm bump` **computes** the next version from the API diff; `elm diff` shows deltas between any two published versions; **`elm publish` refuses uploads whose bump is smaller than computed**. PATCH = identical API; MINOR = additions only; MAJOR = anything changed/removed — including a union type gaining a constructor (consumers exhaustively match) (https://package.elm-lang.org/, https://github.com/elm-lang/elm-package, https://www.oreilly.com/library/view/why-elm/9781491990728/ch05.html). (b) Nearly fully mechanical — the **registry** is the enforcement point; the author doesn't get a vote. (d) The canonical counterexample, filed against elm-lang.org's "enforces semver precisely" claim: change `maxSize = 3` to `-3` and ship as PATCH — types identical, documented contract broken; "an API is more than its types" (https://github.com/elm/elm-lang.org/issues/868). 2023 community assessment: enforcement covers "won't compile" breakage only; you're free to break code in the "it's buggy now" sense; proposed fixes included test-based compatibility checking (https://discourse.elm-lang.org/t/semver-enforcement/9263). Other ecosystems cite it as the model (https://discourse.julialang.org/t/enforce-semver-like-elm/6026, https://news.ycombinator.com/item?id=19075033). (e) **The version number as a derived artifact of a mechanical contract diff**, enforced at publish. Direct transfer to capsules: make the *test suite* the diffed surface — removing/relaxing a spec test computes a major bump; the shared gap across all four tools (behavior) is exactly the slot an executable-spec suite fills.

## 6. Design-by-Contract Lineage

**Eiffel DbC.** (a) `require`/`ensure`(+`old`)/class invariants in the language, inherited with Liskov rules (subclass weakens pre, strengthens post), runtime-checked, rendered into docs (https://www.eiffel.com/values/design-by-contract/). (b) Mechanical only for inputs actually exercised; contract *completeness* is social (`ensure true` passes). (d) Why it never went mainstream: DbC only works "tightly integrated with the fabric of the language"; Eiffel was hobbled by ~$5k/seat licensing (https://slashdot.org/story/07/03/10/009237/why-is-design-by-contract-not-more-popular, Meyer's own analysis https://arxiv.org/pdf/2211.16597). **JML**: runtime checker unmaintained, perpetually chasing Java's evolution (https://sourceforge.net/p/jmlspecs/wiki/Home/). **Microsoft Code Contracts**: never ported to .NET Core, "aren't supported in .NET 5+," repo archived July 2023 — it depended on IL-rewriting outside the compiler, so every toolchain change broke it; Microsoft kept only nullability by moving it *into* the type system (https://github.com/microsoft/CodeContracts, https://learn.microsoft.com/en-us/dotnet/framework/debug-trace-profile/code-contracts). (e) Contracts must live in the artifact that survives regeneration and be enforced by the toolchain, not a sidecar — for capsules: pre/post conditions belong in the spec/test layer, not the implementation.

**Property-based testing (Hypothesis, fast-check).** (a) Properties = universally-quantified executable postconditions; generators + **shrinking** to minimal counterexamples; Hypothesis stateful testing generates and shrinks operation *sequences* against invariants (https://hypothesis.readthedocs.io/, https://fast-check.dev/). (c) Breaking change surfaces as a concrete minimal counterexample; refactors pass because properties name behavior, never structure. (d) Flaky CI, weak properties giving false confidence, property-writing as a spec-design act teams skip. (e) Properties+generators are the ideal **regeneration-stable contract format** — and with the old implementation as oracle you get differential properties for free.

**Mutation testing (pitest, Stryker, mutmut).** (a) Inject syntactic faults; surviving mutants = behavior the tests don't pin down (https://pitest.org/, https://stryker-mutator.io/). (b) Mutation score is a mechanical measure of **test-suite strength — it verifies the verifier**; the spec-completeness argument is explicit in the literature: mutation analysis "points out… the lack of precision of the contracts" (https://www.researchgate.net/publication/4043805_Usage_of_mutation_testing_as_a_measure_of_test_suite_robustness; mutation-adequate suites subsume structural coverage: https://arxiv.org/pdf/1803.07901). (d) Cost, equivalent mutants, score-gaming. (e) **Mutation score is the acceptance gate for "tests as spec": every surviving mutant is a degree of freedom a regenerated implementation could silently exercise.** The single most load-bearing tool for the capsule regeneration story.

## 7. Snapshot / Golden / Approval / Characterization

**(a) Mechanism.** Record output, commit, diff future runs. Jest `toMatchSnapshot()` / `-u` (https://jestjs.io/docs/snapshot-testing). ApprovalTests (Falco): designed printer + diff-tool reporter + explicit human received→approved promotion (https://github.com/approvals/ApprovalTests.Python, https://se-radio.net/2023/12/se-radio-595-llewelyn-falco-on-approval-testing/). Characterization tests (Feathers): assert what legacy code *does*, not what it should do, to freeze behavior before refactoring (https://en.wikipedia.org/wiki/Characterization_test, https://understandlegacycode.com/blog/characterization-tests-or-approval-tests/).

**(b/c).** Mechanical: byte-equality. Everything semantic is social — the recorded output may never have been correct, and every change (breaking or benign) shows up identically as a diff; classification is 100% human.

**(d) Failure mode: snapshot blindness.** Sapegin's critique: developers "just update snapshots without looking at them at all"; you can "commit code with a bug and a snapshot that ensures that the bug is still there"; one shared-Button change fails hundreds of snapshots (https://medium.com/@sapegin/whats-wrong-with-snapshot-tests-37fbe20dfe8e; rehabilitation: https://kentcdodds.com/blog/effective-snapshot-testing). ApprovalTests' explicit approve step is precisely the countermeasure to `jest -u` being one keystroke.

**(e) Steal.** Characterization is the **bootstrap move** for regenerable systems: record behavior over a generated input corpus, regenerate, diff, then *promote* stable diffs into named properties. And: make approval a designed artifact, never a bulk-overwrite flag.

## 8. TLA+ / Dafny / LLM-Verified Code

**TLA+.** Verifies the **design/model, not the code** — no way to check existing code matches the spec (https://www.hillelwayne.com/post/why-dont-people-use-formal-methods/). AWS (Newcombe et al., CACM 2015): used since 2011 on DynamoDB/S3; found a **35-step** replication bug testing would never reach (https://cacm.acm.org/research/how-amazon-web-services-uses-formal-methods/). Niche because of notation friction and the model-code gap — a spec disconnected from code is "just outdated documentation" (industrial SLR: https://arxiv.org/pdf/2411.13722). Wayne's full-code-verification costs: IronFleet ~4 verified lines/person-day, seL4 ~2.

**Dafny.** Pre/post/invariants in the language, SMT-discharged at compile time, compiles to C#/Java/Go/Python — closes DbC's enforcement gap (proof for *all* inputs) at proof-annotation cost; underspecified `ensures` still verifies trivially (https://dafny.org/).

**LLMs × verification, 2024–2026 (active frontier).**
- **Clover** (Stanford/VMware): consistency-checks code↔docstring↔formal annotations pairwise; **100% rejection of incorrect examples** on CloverBench — no single artifact has to be trusted (https://arxiv.org/abs/2310.17807).
- **AlphaVerus** (CMU): bootstraps verified Rust (Verus) generation via verifier-error-driven tree search — with the load-bearing negative result: **the verifier gets reward-hacked** (vacuous specs, `assume` tricks), so a critique/filter phase is required (https://arxiv.org/abs/2412.06176).
- **DafnyBench**: 782 problems; frontier models now high (Opus 4.1: 89.2% pass@10) (https://arxiv.org/html/2601.05385); spec-*generation* benchmarks emerging (Verina https://arxiv.org/pdf/2505.23135; CodeSpecBench for executable behavioral specs https://arxiv.org/html/2604.12268v1); RL using negative tests as a spec-completeness reward — mutation testing reborn as a training signal (https://arxiv.org/pdf/2604.05820).
- **AWS Cedar — the production template**: small verified Lean model (~10× smaller than production) + **differential random testing** proving the production Rust matches it; proofs found 4 bugs, differential/property testing found 21 more; direct Rust verification was judged not ready, so the model-code gap was bridged *statistically* (https://www.amazon.science/publications/how-we-built-cedar-a-verification-guided-approach, https://lean-lang.org/use-cases/cedar/).
- Caveat on NL→spec: LLMs pattern-match famous specs — one produced an "Etcd spec" that was really the Raft paper's spec: model-checks, wrong subject (https://www.sigops.org/2026/can-llms-model-real-world-systems-in-tla/).

**(e) Steal.** Cedar's architecture is the capsule blueprint scaled up: durable small reference model/spec, disposable implementations accepted only via differential testing; Clover adds the multi-artifact consistency loop; AlphaVerus adds the warning that any mechanical gate an LLM optimizes against will be gamed — so the spec layer itself needs adversarial audit (which is exactly mutation testing).

## Q1: Best-known mechanism for keeping mocks/test-doubles faithful

Two mechanisms, at two scales — both called "contract tests":

1. **Shared contract suite run against both fake and real** (the strongest pattern). Write one test suite against the dependency's public interface and run it against both the real implementation and the in-memory fake; the fake is then a **verified fake**. Canonical writeups: Itamar Turner-Trauring's "Fast tests for slow services: why you should use verified fakes" (https://pythonspeed.com/articles/verified-fakes/), Shai Yallin's "Using Contract Tests for reliable memory fakes" (https://www.shaiyallin.com/post/using-contract-tests-for-reliable-memory-fakes), ploeh "Fakes are Test Doubles with contracts" (https://blog.ploeh.dk/2023/11/13/fakes-are-test-doubles-with-contracts/). The institutional version is in *Software Engineering at Google* ch. 13: a fake should be **maintained by the service owners** and shipped alongside the service, with contract tests proving equivalence — "don't create your own fake unless you can ensure its behavior will stay in sync" (https://abseil.io/resources/swe-book/html/ch13.html). Martin Fowler's ContractTest bliki names the exact problem: doubles avoid nondeterminism, "but you need Contract Tests to ensure they remain consistent with the real services" (https://martinfowler.com/bliki/ContractTest.html). Known limit: contract tests can't verify error-path fidelity that's hard to trigger against the real service (network failures, provider bugs).
2. **Verified/verifying doubles** (structural, cheaper, weaker). rspec-mocks `instance_double`/`class_double` check at test time that stubbed methods actually exist on the real class with matching arity — killing interface-level mock drift, not behavioral drift (https://rspec.info/features/3-12/rspec-mocks/verifying-doubles/instance-doubles/, https://semaphore.io/community/tutorials/introduction-to-verifying-doubles-in-rspec). This is the type-check tier; the shared-suite pattern is the behavior tier.
3. Pact itself is the distributed version of the same idea: the consumer's mock (pact file) is replayed against the real provider — the pact *is* the mock-fidelity check across a network boundary.

For capsules: the composite answer is **owner-shipped fakes + one contract suite that both implementations must pass** — the fake and the real provider are just two implementations of the same capsule contract.

## Q2: Is "tests as spec" sufficient for regeneration? Documented cases 2024–2026

**No consensus that tests alone suffice — the empirical evidence says they don't, and the emerging practice is spec+tests hybrids.**

- **The direct counter-evidence is the patch-overfitting literature** (automated program repair — regeneration's precursor): a patch passing the full suite is only "plausible"; "limited test suites only weakly approximate program specifications, so a patched program can satisfy requirements encoded in test cases while presenting significantly different behavior outside of those tests." Measured rates: **73–81% of APR patches overfit** on C benchmarks (Patch Overfitting survey: https://www.researchgate.net/publication/385012043_Patch_Overfitting_in_Program_Repair_A_Survey; test-gen detection of overfitted patches: https://www.researchgate.net/publication/318375339). This is the quantified version of "your tests underdetermine the behavior."
- **Documented regeneration practice (2024–2026)** is spec-driven, with tests as the enforcement half, not the whole spec: GitHub **Spec Kit** (93k+ stars; GitHub itself calls it an experiment), AWS **Kiro**, **Tessl** (Podjarny, ~$125M raised; explicit "spec is source of truth, implementations regenerated, tests bound to spec assertions" — but its regeneration engine is closed beta, 1:1 spec-to-file, and "demonstrably non-deterministic": https://codemyspec.com/blog/tessl-review, https://tessl.io/podcast/revolutionising-spec-driven-development-with-tessl-s-framework-registry/). Thoughtworks' assessment of SDD: https://www.thoughtworks.com/en-us/insights/blog/agile-engineering-practices/spec-driven-development-unpacking-2025-new-engineering-practices. Documented wins are bounded and specific — **Airbnb migrated 3,500 test files in six weeks vs an estimated 1.5 years** (test *migration*, notably — the one case where tests literally were the regenerable artifact) (https://dev.to/krlz/spec-driven-development-in-2026-what-it-is-the-tooling-and-how-teams-actually-use-it-2fk2). Criticisms on record: "sea of markdown," review overload, "reinvented waterfall," false sense of control when agents ignore parts of the spec (https://codemyspec.com/blog/spec-driven-development, https://www.marktechpost.com/2026/05/08/9-best-ai-tools-for-spec-driven-development-in-2026-kiro-bmad-gsd-and-more-compare/).
- **The convergent answer for regeneration confidence** across research and practice: tests + properties + differential/characterization runs + mutation score. Property-based testing is explicitly recommended in SDD literature to absorb LLM non-determinism ("verify invariants from specs are satisfied regardless of implementation variation": https://arxiv.org/html/2602.00180v1); Cedar's differential-testing bridge and AlphaVerus's reward-hacking finding supply the formal-methods end of the same conclusion.

**Bottom line for the capsule architecture:** every mature system in this survey mechanically verifies structure and is blind to behavior — Elm proves structural enforcement can be total (registry-computed versions), and the patch-overfitting numbers prove example-based tests alone leave 70%+ freedom. The composite that the evidence supports: properties+generators as the durable contract format, characterization corpus + differential testing against the previous implementation as the regeneration gate, **mutation score as the mechanical answer to "is this capsule's spec tight enough to permit regeneration"**, Elm-style computed compatibility verdicts at the capsule boundary (relaxed/removed test ⇒ major bump), Pact-style pending/can-i-deploy lifecycle for cross-capsule expectations, and an adversarial spec audit because any gate an LLM optimizes against will be gamed.

# Research: Strong In-Process Modularity — Organizational War Stories

Provenance: research-agent sweep, 2026-07-24. Preserved verbatim as evidence base; synthesis lives in `../prior-art.md`.

## 1. Shopify + Packwerk (and Gusto)

**(a)** Packwerk (Sept 2020) is static analysis over Ruby constant references that enforces declared package boundaries (dependency + privacy checks), with `package_todo.yml` files baselining existing violations for gradual burn-down. Shopify used it to componentize the world's largest Rails monolith ("Under Deconstruction," 2020).

**(b) What happened** — the definitive source is Shopify's own **"A Packwerk Retrospective"** (Jan 2024, railsatscale.com), which is remarkably close to a mea culpa:

- **Todo-file graveyards are real.** Todo files grew faster than teams burned them down. The retro authors say they were "likely the first Packwerk user to completely work through an entire package todo file, years after its initial release." Baselining made violations ambient wallpaper instead of pressure.
- **Privacy checker degenerated and was deleted.** Privacy checks "transformed Packwerk into something it was never intended to be: an API design tool" — producing poorly documented public APIs dumped into cargo-cult `app/public` directories. **Removed in Packwerk 3.0.**
- **Aspirational graphs vs. running code.** "Developers tend to group code into packages based strongly on semantic clues that in many cases have little relation to how the code actually runs." A `billing` model doing fraud detection actually belongs in the platform base layer. Their conclusion: bend your mental model to the code, not vice versa — "running code, more than any metric, will always be the best indicator of real progress."
- **Static-analysis blind spots**: `require`/`autoload` loads, Rails engine implicit deps (routes, initializers, fixtures) — a package with zero violations could still NameError at runtime.
- **Where they ended up (~2024)**: functional layering (a zero-dependency "Platform Essentials" base package, like ActiveSupport) with domain components nested above; Packwerk demoted from "primary modularization strategy" to a ratchet preventing new violations at critical layers. The cultural coda came at Rails World 2024: Eileen Uchitelle's "architecture cannot fix human problems" talk (testdouble.com write-up).
- **Gusto**: leaned in harder than Shopify — built the `rubyatscale` / "packs" gem ecosystem, `pks` (Rust rewrite of packwerk, which they now use instead), CODEOWNERS-per-pack. Hagemann's "Gusto's Gradual Modularization Destination" answers "where does this end?": not gems/engines/services but **nested packs inside ~20 "product services"** — i.e., the destination is organized ownership, not extraction. His book "Gradual Modularization for Ruby and Rails" argues the value is per-step, not from reaching an end state.

**(c) Degeneration mode**: todo-file baselining as permanent amnesty; privacy enforcement mutating into bad API design; aspirational dependency graphs diverging from runtime truth.
**(d) Steal**: the "running code over philosophy" test — validate a boundary by actually running/loading the module standalone, not just by static check; and a zero-dependency platform base package. **Avoid**: any baseline/todo mechanism without a hard ratchet + owner + deadline; a "public API" folder convention without documentation/design pressure.

Sources: https://railsatscale.com/2024-01-26-a-packwerk-retrospective/ · https://shopify.engineering/shopify-monolith · https://shopify.engineering/enforcing-modularity-rails-apps-packwerk · https://engineering.gusto.com/gustos-gradual-modularization-destination-48d7aabbdede · https://engineering.gusto.com/the-current-state-of-gustos-modularity-tooling-c99f345fd0a7 · https://engineering.gusto.com/a-how-to-guide-to-ruby-packs-gustos-gem-ecosystem-for-modularizing-ruby-applications-e236126b8c2c · https://testdouble.com/insights/rails-world-eileen-uchitelle-team-culture-over-architecture · https://www.babbel.com/en/magazine/modularizing-our-rails-monolith-with-packwerk · https://medium.com/pennylane-engineering/scaling-our-ruby-on-rails-monolith-using-packwerk-part-1-b787aaa218ff

## 2. Self-Contained Systems (SCS)

**(a)** SCS (INNOQ's scs-architecture.org): split by business capability into systems that each own **UI + logic + database**, integrate preferably via links/UI composition or async, never share a DB; each SCS owned by one team. It's "microservices done right at macro granularity" — few, coarse, autonomous systems.
**(b)** Flagship adoption: **Otto.de** rebuilt its shop as ~a dozen "verticals" (85% of revenue through them), one team per customer-journey step, fat JARs + Docker + CD; later dissected verticals into microservices internally as they grew. Also Zalando, REWE, Swissquote. It stayed niche because: it demands async/eventual-consistency thinking and UI-composition discipline up-front; it was a consultancy-branded pattern competing against the Netflix-backed microservices hype wave; and it offers no incremental adoption story for an existing monolith.
**(c) Degeneration**: individual SCS re-grow into monoliths internally (Otto's own verticals needed re-dissection); UI composition without a shared design system fragments UX.
**(d) Steal**: "each capsule owns its full slice including UI and data; integration via links/events, not shared DB" — the cleanest autonomy definition in the literature. **Avoid**: making the unit so coarse that a capsule becomes a monolith needing its own modularization program.

Sources: https://scs-architecture.org/why.html · https://www.otto.de/jobs/en/technology/techblog/blogpost/on-monoliths-and-microservices_2015-09-30.php · https://www.infoq.com/articles/scs-microservices-done-right/ · https://www.innoq.com/en/articles/2016/11/self-contained-systems-different-microservices/ · https://en.wikipedia.org/wiki/Self-contained_system_(software)

## 3. DDD Bounded Contexts + Context Mapping

**(a)** A bounded context is the scope within which a model's terms are consistent; **context mapping** names the *relationship types* between contexts: **Shared Kernel** (jointly owned model subset, changes require both teams), **Customer/Supplier** (downstream can negotiate upstream's roadmap), **Conformist** (downstream swallows upstream's model wholesale, no negotiation power), **Anti-Corruption Layer** (downstream translates upstream's model at the boundary), plus Open Host Service / Published Language, Separate Ways, Partnership.
**(b)** The mapping vocabulary stuck (it's really an org-chart honesty tool — each pattern encodes *who bends when the other side changes*); the tactical patterns (aggregates/repositories/factories) are where the ceremony criticism concentrates. INNOQ's "Is DDD overrated?", Khalil Stemmler's take, CodeOpinion's "Stop doing dogmatic DDD," and James Hickey's "Stop pretending to do DDD" all converge: teams cargo-cult entities/repositories ("DDD-Lite") while skipping bounded contexts — the only part that matters at module scale; bounded contexts themselves are "just modular design" rediscovered.
**(c) Degeneration**: tactical-pattern ceremony without strategic boundaries; one "enterprise-wide canonical model" masquerading as a shared kernel.
**(d) Steal**: use the context-map relationship names as **machine-readable edge types between capsules** (an edge isn't just "depends on" — it's conformist vs. ACL vs. customer-supplier, which tells an agent how defensively to code the boundary). **Avoid**: importing aggregate/repository/value-object ceremony as a requirement of the module system.

Sources: https://github.com/ddd-crew/context-mapping · https://deviq.com/domain-driven-design/context-mapping/ · https://pubs.opengroup.org/architecture/o-aa-standard/DDD-strategic-patterns.html · https://www.innoq.com/en/blog/2021/03/is-domain-driven-design-overrated/ · https://khalilstemmler.com/blogs/domain-driven-design/is-ddd-overrated/ · https://codeopinion.com/stop-doing-dogmatic-domain-driven-design/ · https://www.jamesmichaelhickey.com/stop-pretending-domain-driven-design/

## 4. Vertical Slice Architecture & Feature-Sliced Design

**VSA (Bogard, 2018)**: (a) organize by feature/request, not by layer — each slice contains its full handler stack (typically MediatR request→handler in .NET); minimize coupling *between* slices, maximize cohesion *within* one. Born from his 2-year onion/clean-architecture project where strict layer rules made change impact opaque. (b) Stuck in the .NET world as the standard anti-clean-architecture position. (c) Degeneration: slice-to-slice coupling sneaks back via shared handlers; and semantic diffusion — people read it as "no shared code ever," duplicate everything, then blame the pattern (Bogard only said *minimize* coupling; push shared behavior down when duplication hurts). Critiques: architecture-weekly's "My thoughts on Vertical Slices, CQRS, Semantic Diffusion"; ricofritzsche.me "Why Vertical Slices Won't Evolve from Clean Architecture."
**FSD (feature-sliced.design)**: (a) frontend methodology: fixed **layers** (app → pages → widgets → features → entities → shared) × **slices** (business domains) × **segments** (ui/model/api), with a hard rule that imports only point downward, lint-enforced (`steiger`/eslint plugins). (b) Big in the Russian/Eastern-European frontend scene, spreading via fintech/e-commerce; the closest existing thing to "machine-checked frontend capsules." (c) Degeneration: over-engineering for small apps; endless "is this a feature or an entity or a widget?" taxonomy debates; the `shared` layer becomes the junk drawer (their own docs warn about it); painful retrofits onto legacy code. (d) **Steal from both**: FSD's *lint-enforced one-way layer imports* and public-API-per-slice (`index.ts` re-export as the only legal entry). **Avoid**: FSD's fixed six-layer taxonomy (classification arguments are pure ceremony for agents); VSA's ambiguity about where cross-slice shared behavior lives.

Sources: https://www.jimmybogard.com/vertical-slice-architecture/ · https://jeremiahflaga.github.io/2019/05/20/vertical-slice-architecture-is-it-incompatible-with-clean-architecture/ · https://www.architecture-weekly.com/p/my-thoughts-on-vertical-slices-cqrs · https://ricofritzsche.me/why-vertical-slices-wont-evolve-from-clean-architecture/ · https://feature-sliced.design/ · https://medium.com/@lightxdesign55/the-drawbacks-of-feature-sliced-design-b19206b96cb7 · https://dev.to/m_midas/feature-sliced-design-the-best-frontend-architecture-4noj

## 5. Modular Monolith Movement (2020–2026) + Spring Modulith

**(a)** One deployable, hard internal boundaries. Canon: **Kamil Grzybek's** 5-part series (Primer / Architectural Drivers / **Architecture Enforcement** / Integration Styles / Domain-Centric Design) + his `modular-monolith-with-ddd` repo (~12k stars); Simon Brown's "modular monolith first"; Milan Jovanovic's .NET essay/course ecosystem. Thesis: the industry "false-started" into microservices to escape big-ball-of-mud problems that are actually discipline problems.
**(b)** Enforcement tooling is what made this generation different from 2005-era "packages": JVM → ArchUnit + **Spring Modulith**; .NET → NetArchTest.Rules / ArchUnitNET architecture tests (Jovanovic: "reduce the cost of enforcing your architecture to zero"); Ruby → packwerk/pks; JS/TS → eslint boundary plugins, Nx module boundary tags.
**(c) Spring Modulith specifics — closest JVM analog to capsules:**
- **Convention**: every direct sub-package of the app root = a module; the module's top-level package is its public API; sub-packages are internal by default. Optional `package-info` `@ApplicationModule(allowedDependencies=…)` for an explicit allow-list; "named interfaces" expose additional API packages; "open modules" opt out.
- **Verification**: `ApplicationModules.of(App.class).verify()` in a plain JUnit test (2.0 can also verify at startup), backed by ArchUnit. Rejects (1) module dependency cycles, (2) any reference into another module's internals, (3) non-allow-listed dependencies. `detectViolations()` returns the list for filtering/baselining; `VerificationOptions` adds custom rules (e.g., jMolecules hexagonal rules).
- **Generated docs**: `Documenter` writes, from the *same runtime model*, C4/UML PlantUML component diagrams (whole system + per-module), and an **Application Module Canvas** per module: base package, Spring beans, aggregate roots, **published events, listened-to events**, config properties — regenerated on every test run, so docs cannot go stale. This is exactly the "boundary spec + generated capsule doc" idea, shipped.
- **Testing**: `@ApplicationModuleTest` bootstraps *one module* (optionally + its declared deps); `PublishedEvents` asserts what a use case emitted; the `Scenario` DSL does stimulus→expected-event/state without wiring downstream modules.
- Module integration style is event-first (`@ApplicationModuleListener`, transactional outbox-style event publication registry) to keep edges observable.
**(d) Steal**: verification-as-a-test (violations fail CI, no separate tool), and doc generation from the *verified model* so spec/doc/code can't diverge. **Avoid**: package-convention-only boundaries with no runtime story — Modulith modules still share one process/DB/transaction, so "extractability" claims stay theoretical until exercised (same trap Shopify named).

Sources: https://www.kamilgrzybek.com/blog/posts/modular-monolith-primer · https://github.com/kgrzybek/modular-monolith-with-ddd · https://docs.spring.io/spring-modulith/reference/verification.html · https://docs.spring.io/spring-modulith/reference/documentation.html · https://docs.spring.io/spring-modulith/reference/testing.html · https://spring.io/blog/2022/10/21/introducing-spring-modulith/ · https://milanjovanovic.tech/blog/shift-left-with-architecture-testing-in-dotnet · https://milanjovanovic.tech/blog/5-architecture-tests-you-should-add-to-your-dotnet-projects · https://www.baeldung.com/spring-modulith

## 6. Plugin / Microkernel: Eclipse RCP vs VS Code, Kubernetes

**(a)** Microkernel = tiny host + everything as plugins against extension points. Eclipse: OSGi bundles, in-process, arbitrary plugin→plugin dependency graph, extension registry. VS Code: extensions run in a **separate extension-host process** against **one versioned, backward-compatible API**, with declarative contribution points + lazy activation events.
**(b/c)** Eclipse's pain: plugins share the UI thread/process (one bad plugin hangs the IDE); a huge inter-plugin dependency graph plus Eclipse-specific APIs duplicating OSGi (backward-compat layering); classloader hell. VS Code's fixes are structural: crash/perf isolation via process boundary; the dependency graph is "mostly a simple tree of depth one" (every extension depends on the API, rarely on each other); extensions can't touch the DOM at all — the host mediates everything. Eclipse itself conceded the direction with Theia (VS Code-extension-compatible). **Kubernetes controller pattern** (briefly): every module is a reconciliation loop watching declared desired state on a shared API server and converging actual state; modules never call each other — they communicate through the state store. The strongest known pattern for *uncoordinated* module authorship (https://kubernetes.io/docs/concepts/architecture/controller/).
**(d) Steal**: one narrow versioned platform API that capsules depend on, instead of capsule→capsule imports ("tree of depth one" is a measurable target); declarative manifests + lazy activation. **Avoid**: letting capsules extend each other via a general extension registry — that's how Eclipse's graph became unmanageable.

Sources: https://www.eclipse.org/articles/Article-Plug-in-architecture/plugin_architecture.html · http://moi.vonos.net/java/eclipse4-architecture/ · https://www.eclipse.org/community/eclipse_newsletter/2018/october/theia.php · https://code.visualstudio.com/api/advanced-topics/extension-host

## 7. Micro-Frontends

**(a)** Independently built/deployed frontend fragments composed at runtime (iframes, ESI, Module Federation) so team deployment autonomy extends to the UI.
**(b) Worked**: DAZN (Mezzalira's client-side orchestration), IKEA (ESI server-side composition), Zalando (Project Mosaic/Tailor enabled many teams on one storefront). **Degenerated**: Zalando's own retro — Mosaic's freedom in "tech stacks, bundling, and deployment practices across fragments led to inconsistent user experience and cross-team collaboration difficulties" → replaced Mosaic with a centralized **Rendering Engine / Interface Framework** (teams now supply declarative "renderers" inside one managed runtime; ~90% of traffic). Spotify ran iframe-per-page MFEs in the old desktop client, then consolidated onto one shared web-player codebase to stop building features twice. Grass-roots post-mortems ("We killed our micro-frontend project") list the recurring costs: a build pipeline/repo/deploy config per fragment, React 17-vs-18 version skew forking shared libraries, design systems styled-around into a "collage," debugging across builds/sourcemaps as "archaeology."
**(c) Degeneration mode**: per-module infra overhead compounding, dependency-version skew, UX fragmentation — runtime independence costing more than the team autonomy is worth.
**(d) Steal**: Zalando's end-state — **team autonomy over content within one platform-owned runtime** (that's literally "capsules + kernel + boxes"). **Avoid**: runtime composition and per-capsule dependency trees when build-time composition in one repo suffices; MFE pain is the strongest argument that agents/teams need *boundary* independence, not *deployment* independence.

Sources: https://engineering.zalando.com/posts/2021/03/micro-frontends-part1.html · https://engineering.zalando.com/posts/2021/09/micro-frontends-part2.html · https://medium.com/dazn-tech/adopting-a-micro-frontends-architecture-e283e6a3c4f3 · https://www.infoq.com/news/2021/04/spotify-web-desktop-unification/ · https://engineering.atspotify.com/2021/04/building-the-future-of-our-desktop-apps · https://dev.to/tahamjp/why-micro-frontends-failed-us-and-what-were-trying-next-43oo · https://blog.logrocket.com/solving-micro-frontend-challenges-module-federation/

## 8. Cell-Based Architecture / Bulkheads (brief)

**(a)** A cell is a complete, fixed-max-size replica of the whole stack (compute+storage+config); a thin router pins each tenant/partition to one cell; failures stay inside the cell. Bulkheads for services = cells; for data = shards. AWS (re:Invent ARC411, Well-Architected REL, solutions-library guidance) and WSO2's reference architecture are the canon.
**(b/c)** Isolation on the *replication* axis (identical copies, blast-radius capping, safe deploys cell-by-cell), orthogonal to functional modularity; the degeneration risk is the router becoming the new shared single point of failure, and "cross-cell" features eroding the whole point.
**(d) Steal**: the framing "a boundary is only real if a failure demonstrably stops at it" — give capsules a blast-radius story (error containment, per-capsule kill switch), not just an import story. **Avoid**: conflating capsule boundaries with cell boundaries — they solve different problems (change isolation vs. failure isolation).

Sources: https://d1.awsstatic.com/events/reinvent/2019/REPEAT_1_Reducing_blast_radius_with_cell-based_architectures_ARC411-R1.pdf · https://github.com/aws-solutions-library-samples/guidance-for-cell-based-architecture-on-aws · https://wa.aws.amazon.com/wellarchitected/2020-07-02T19-33-23/wat.question.REL_10.en.html · https://github.com/wso2/reference-architecture

## 9. Amazon Lineage (brief)

**(a)** The 1998 **Distributed Computing Manifesto** (published by Vogels 2022: https://www.allthingsdistributed.com/2022/11/amazon-1998-distributed-computing-manifesto.html) → the **2002 Bezos API mandate**: all teams expose data/functionality only through service interfaces; "no direct linking, no direct reads of another team's data store, no back-doors"; all interfaces designed as if externalizable; "anyone who doesn't do this will be fired." Paired with two-pizza teams and Vogels' **"you build it, you run it."**
**(b)** It made module ownership *total*: the team owns interface, implementation, data, and the pager. Operational feedback measurably improved service quality (Vogels), and externalizable interfaces became AWS.
**(c) Degeneration**: unprepared teams drowning in on-call; fear-driven cultures hiding production issues; and the mandate's cost — everything is a network call and org boundaries ossify into API boundaries (Conway locked in by decree).
**(d) Steal**: "no back-doors, interfaces designed as externalizable" as the capsule contract test — if a capsule's API couldn't survive being consumed by a stranger (or a strange agent), it isn't an API; plus ownership including the module's operational/test health, not just its code. **Avoid**: interpreting it as "every boundary must be a network hop."

Sources: https://konghq.com/blog/enterprise/api-mandate · https://nordicapis.com/the-bezos-api-mandate-amazons-manifesto-for-externalization/ · https://aws.amazon.com/builders-library/operational-excellence-at-amazon · https://www.equalexperts.com/blog/our-thinking/what-is-you-build-it-you-run-it/ · https://www.stevesmith.tech/blog/you-build-it-you-run-it/

## The Three Specific Questions

**Q1 — Who owns integration tests between modules?** The literature has no clean answer; it has a named failure: "coverage that exists on paper where nobody is accountable" — when service A changes its schema and B's expectations break, *no one owns the failing test* (vfunction, semaphore, softwaremill). The workable consensus positions: (1) **consumer-driven contract tests** — the *consumer* writes the expectations, the *provider* runs them in its CI (Pact, microservices.io "service integration contract test") — ownership split by direction: consumer owns the assertion, provider owns keeping it green; (2) **Spring Modulith's answer for in-process modules**: don't write cross-module integration tests at all — each module's `@ApplicationModuleTest` asserts its *emitted events* (its outbound contract) via `Scenario`/`PublishedEvents`, and the boundary verification test is owned by the platform; (3) a central QA/platform team owning cross-module E2E is repeatedly described as the drift-prone fallback. For capsules: consumer capsule owns the contract expectation, provider capsule's CI must run it, kernel owns the verifier itself.
Sources: https://microservices.io/patterns/testing/service-integration-contract-test.html · https://pact.io/ · https://softwaremill.com/testing-microservices-contract-tests/ · https://vfunction.com/blog/microservices-testing/ · https://docs.spring.io/spring-modulith/reference/testing.html

**Q2 — Shared-kernel scope creep.** Documented failure modes: "tragedy of the commons"; governance cost "explodes" once the participating-team count grows ("a shared kernel is for a small cluster of closely related contexts, not the whole enterprise"); and the category error of stuffing *technical* commonality into a *domain* kernel — "a utility library is not a shared kernel; logging wrappers, date helpers, HTTP clients belong elsewhere." Containment tactics across sources: admit only concepts that are **stable AND genuinely shared** (IDs, code sets, classification rules, serialization contracts); never process/business logic; explicit change-review + breaking-change policy + ownership matrix; keep participant count small; when it swells, demote pieces to Published Language / Open Host Service or just duplicate ("Separate Ways" — duplication is cheaper than coupling for unstable concepts). The Shopify corroboration: their surviving base package, Platform Essentials, is *functional* infrastructure with **zero dependencies** — the kernel stayed containable precisely because it's the ActiveSupport-shaped bottom of the graph, not a "common domain" grab-bag. Gusto's equivalent is enforced layering in packs (lower layers can't reach up). Practical rule for capsules: the kernel is allowed to be depended on, never to depend; anything with churn gets evicted to a capsule.
Sources: https://buildsimple.substack.com/p/strategic-ddd-the-balancing-act-of · https://deviq.com/domain-driven-design/shared-kernel/ · https://www.nilus.be/blog/shared_kernel_in_domain-driven_design_microservices/ · https://alok-mishra.com/2021/11/03/ddd-anti-patterns/ · https://railsatscale.com/2024-01-26-a-packwerk-retrospective/

**Q3 — Spring Modulith mechanics**: covered in §5 (convention→model via `ApplicationModules.of()`, ArchUnit-backed `verify()` for cycles/internal-access/allow-lists, `detectViolations()` for baselining, `Documenter` generating C4 PlantUML + per-module Canvas — beans, aggregates, published/listened events, config props — regenerated every test run, `@ApplicationModuleTest` + `Scenario` for module-scoped verification). Key design choices for capsules: verification runs as an ordinary test (zero extra tooling), docs are derived from the verified model (can't drift), and events are first-class boundary citizens (the Canvas documents what a module emits/consumes — that's the integration contract).

**Cross-cutting pattern worth naming**: every one of these efforts that degenerated did so the same way — the enforcement mechanism became a *ledger of exceptions* (packwerk todos, ignored ArchUnit freezes, MFE shared-dep overrides) with no owner and no ratchet. Every one that held up bound the check to something that already runs on every change (CI test, build failure, startup verification) and generated its human-facing artifacts from the same model it verified.

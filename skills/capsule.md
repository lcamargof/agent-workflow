# Capsule Skill

Use this when creating a capsule, working inside one (a directory containing `CONTRACT.md`), or changing any capsule's contract. Skip for repos/directories without capsules and for pure platform-kernel work (that's max-radius by definition — treat as high profile in `workflow.md`).

Status: design-phase. Tooling (`capsule-lint`, graph check) is not built yet; until it lands, every "run X" step below is performed manually and its result recorded. Behavioral confidence: unproven — no live-agent pressure scenario has run. Reference design: `docs/capsules/design.md` (kit repo); do not restate it here — this file owns behavior, that file owns rationale.

## Rules always in force

- The contract's machine block is derived/verified, never hand-trusted: `provides` is generated from the public surface; `requires` actuals are derived from code and diffed against declared policy. If you edited either by hand without regenerating, the work is not done.
- Consumers are a graph query. Never write a consumer list into any file.
- Risk is derived from channels (money, auth, on-chain, PII ⇒ floor). You may raise a capsule's risk tier; you may never lower it below the derived floor.
- Prose invariants: ≤ ~20 lines, only guarantees a consumer would be burned by. New frontmatter fields require a recorded incident that the field would have prevented.
- Work happens inside the capsule. Needing to read another capsule's internals is a boundary bug: record it in the capsule's docs and either fix the contract or route the finding — do not silently widen your context.

## Working inside a capsule (contract unchanged)

1. Load `CONTRACT.md` + the capsule's `AGENTS.md`-linked doc for the area. Done when you can state the invariants you must not break.
2. Implement against declared dependencies only; consume other capsules via their fakes.
3. Run the capsule's `verify` command in isolation (only declared deps present). Done when green **and** the boundary check reports no new edges. A green suite with an undeclared import is a failure, not a pass.
4. Self-review vs the invariants; ship at local radius. No cross-capsule review needed.

## Changing a contract

1. Land the contract diff first, separately from implementation: regenerate `provides`, update policy, let the version be computed (surface or contract-test removal/relaxation ⇒ major). Done when the diff shows the computed bump and the signed block is regenerated by the verifier.
2. The consumer closure enters scope automatically — list it from the graph, run consumers' contract suites. Done when every consumer edge is green or has a pending expectation recorded against it.
3. Risk ≥ high, or any change to money/auth/on-chain channels: stop and hand off for human review of the contract diff + evidence. Never self-approve.

## Creating a capsule

1. Qualification gate: stable boundary (survived at least one design iteration), single owner, own test seam. If under active design churn: stay a normal folder; record why.
2. Scaffold from the kit template; write prose invariants and the contract tests **before** implementation. Tests derive from stated intent (the human-owned acceptance shape), not from the implementation you plan to write.
3. Done when: `verify` runs green in isolation, the whole-graph check routes every `requires`, and a cold stranger (agent or human, zero repo context) could state the capsule's purpose and guarantees from `CONTRACT.md` alone.

## Stop conditions

- Undeclared dependency needed to proceed → stop, propose the contract change; never deep-import "temporarily."
- Third contract edit on the same capsule within a month → stop; the boundary is probably wrong (cut along how code runs); trigger a boundary review instead of a fourth edit.
- Regeneration of an implementation: only via the full gate (design.md §6); high-risk capsules always produce a human-review PR.
